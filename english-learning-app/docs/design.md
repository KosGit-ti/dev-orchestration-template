# 詳細設計

要件は `docs/requirements.md`、レベル体系は `docs/level-framework.md`、全体像は `docs/architecture.md` を参照する。本書は実装判断とその理由を残す。

## 1. 認証（FR-020）

### 1.1 なぜクライアント完結か

サーバーを持たない選択の代償は明確である。ブラウザ内で完結する認証は、端末を掌握した攻撃者に対して無力である。それでもこの方式を採ったのは次の理由による。

- 配信先が GitHub Pages（静的配信のみ）であり、認証を検証する相手がいない。
- 守る対象が個人の学習記録であり、金銭・個人情報を扱わない。
- 無料で完結し、外部サービスのアカウント作成も鍵管理も要らない。

この前提はログイン画面と設定画面に日本語で明記してある。機微情報を扱う用途へ転用しない（P-102）。

### 1.2 保存されるもの

```text
eie:auth:accounts:v1   Account[]（password は PasswordHash のみ）
eie:auth:session:v1    Session（token / userId / 有効期限）
eie:progress:<userId>:v2  Progress
eie:theme:v1           ThemePreference
```

`Account.password` は `{ algorithm, iterations, salt, hash }` であり、素のパスワードは書かない。

### 1.3 ハッシュ

PBKDF2-HMAC-SHA256 / 600,000 回 / ソルト 16 バイト / 導出鍵 256 ビット。反復回数は OWASP の推奨（2023 年時点）に合わせた。WebCrypto のネイティブ実装で走るため、1 回あたり数百ミリ秒に収まる。

比較は長さを揃えたうえで XOR の累積を取る定数時間比較にした。先頭一致からの推測余地を残さないためである。

### 1.4 初期アカウント

`admin` / `shunsuke` を初回起動時に生成する。パスワードはリポジトリに書いてあり、秘密ではない。だから `mustChangePassword: true` を立て、変更するまで学習画面へ入れない。この強制は `AppShell` の 1 箇所で行う。各画面へ書くと必ず抜ける。

秘密でないものを秘密のように扱わない、というのが P-002 の趣旨に対する本設計の答えである。実際の秘密をコミットするより、公開値であることを明示して強制変更をかけるほうが安全側に倒れる。

### 1.5 ユーザー列挙の防止

存在しないユーザー名でも `hashPassword` を 1 回走らせてから同じ失敗理由を返す。応答時間の差でアカウントの有無を読まれないようにするためである。

### 1.6 差し替えの口

`AuthProvider` interface を切り、画面は具象実装を知らない。全メソッドを非同期にしてあるのは、将来サーバー実装へ差し替えたときにシグネチャを変えずに済ませるためである。

## 2. 間隔反復（FR-010）

SM-2 を土台に 2 点変えた。

**評価を 4 段階に絞った。** オリジナルの 6 段階（0〜5）は自己申告のぶれが大きく、個人利用では 3 と 4 の区別が機能しない。again / hard / good / easy に落とし、UI でも「分からなかった / 迷った / 思い出せた / 即答できた」と言い換えている。

**初回と 2 回目の間隔を固定値にした。** 素の SM-2 は ease から間隔を計算するため、学習開始直後に間隔が伸びすぎる。1 日 → 6 日を固定で置き、3 回目以降を ease に委ねる。

`again` は間隔 0 を返す。これは「同一セッション内で再び出す」を意味し、単語モードは該当語をキューの末尾へ戻す。

ease の下限は 1.3。これを割ると間隔が縮み続け、当該語がセッションを占有する。

## 3. 出題（FR-010 / FR-012）

### 3.1 誤答選択肢

同一レベルの語から選ぶ。レベルをまたぐと易しい語が混ざり、消去法で解けてしまう。同一レベルに 3 語未満しかない場合だけ全体から補う。

### 3.2 双方向出題

「定義 → 語」と「語 → 定義」を語 ID とラウンド数から決定的に切り替える。片方向だけだと、選択肢の見た目のパターンで正解を覚えてしまう。

### 3.3 決定性

`Math.random()` を使わず、seed から xorshift で乱数列を作る。同じ seed なら同じ出題順・同じ選択肢配置になるため、テストが決定的に書ける（NFR-001）。

## 4. セッション計画（FR-030）

方針は 2 つ。

1. 期限が来た復習を新規より先に出す。復習が溜まったまま新規を足すと、どのレベルでも遅かれ早かれ破綻する。
2. 復習だけで枠が埋まる日は新規を足さない。目標語数を守るために未学習語を押し込むと、復習の遅れが翌日以降へ積み上がる。

期限超過が大きい語から順に出す。放置した語ほど忘却が進んでいるためである。

## 5. 進捗のスキーマ移行（FR-030）

`Progress.version` を持ち、`migrate()` が変換する。現在は v1 → v2（日次記録の追加）に対応する。

未知の版は空の進捗へ倒す。解釈できないデータを推測で読むと、壊れた状態のまま学習が続いて原因が消える。フェイルクローズ（P-010）の適用である。

スキーマを増やすときは移行関数とテストを同一変更に含める（P-104）。

## 6. 配色（FR-040）

CSS 変数を単一の正本にし、Tailwind はその変数を参照するだけにした。`:root` にライト、`.dark` にダークを置く。`prefers-color-scheme` のメディアクエリは CSS に書かない。OS 追従は `ThemeProvider` が `.dark` クラスの付け外しへ翻訳する。

こうしないとトークンの定義箇所が 2 つになり、「システム追従では直ったがダーク指定では直らない」種類の不整合が入る。

初回描画のちらつきは、`<head>` に同期スクリプトを差し込んで body 描画前に `.dark` を付けることで防ぐ。

## 7. 音声（FR-010 / FR-011）

Web Speech API を直接呼ぶ。外部 TTS API を使わない理由は、無料であること、オフラインで動く端末が多いこと、そして第一目的に必要な「音と意味の結び付け」が端末の音声で足りることによる。

未対応環境では機能自体を出さない。エラーを出しても学習者にできることが無い。

## 8. オフライン（FR-050）

Service Worker はページ遷移を network-first、静的アセットを stale-while-revalidate で扱う。ページを cache-first にすると更新が反映されず、原因の分かりにくい不具合になる。

開発中は登録しない。古いキャッシュで変更が見えない事故を避けるためである。

## 9. コンテンツ検証（FR-001）

`web/scripts/validate-content.ts` が CI と完了ゲート G-5 から呼ばれる。落とすのは 4 種類。

1. 日本語（かな・カタカナ・漢字）の混入
2. ID 重複、レベル不一致、必須項目欠落
3. 本文中プレースホルダ `{{n}}` と穴埋め設問の不一致
4. 選択肢に正解が無い、または重複している設問

警告だけ出して通す段は置かない。通るか落ちるかのどちらかにする。
