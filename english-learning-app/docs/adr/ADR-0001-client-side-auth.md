# ADR-0001 認証をクライアント完結で実装する

- 状態: 採用
- 日付: 2026-08-18
- 関連: FR-020 / P-102 / C-002 / C-003 / C-004

## 背景

ログイン機能（admin と shunsuke の 2 アカウント）が要件にある。一方で配信先は GitHub Pages などの静的ホスティングであり、サーバーサイドの処理を置けない。無料で完結させることも要件に含まれる。

## 選択肢

1. **クライアント完結**：パスワードをブラウザ内でハッシュ化し、localStorage へ保存する。
2. **Supabase 無料枠**：実サーバー認証を使い、複数端末で進捗を同期する。
3. **Cloudflare Workers 等の自前バックエンド**：認証エンドポイントを自分で書く。

## 決定

選択肢 1（クライアント完結）を採用する。ただし `AuthProvider` interface を切り、選択肢 2 へ差し替えられる構造にする。

## 理由

- 外部サービスのアカウント作成も API キー管理も不要で、要件の「無料」を完全に満たす。
- 守る対象が個人の学習記録であり、金銭・個人情報を扱わない。
- オフラインで動く。学習アプリとして通信必須にしない利点が大きい。
- Supabase を初期から入れると、鍵の扱い（P-002）と CI の秘密情報管理が初手から必要になり、MVP までの距離が伸びる。

## 代償

**この方式は端末を掌握した攻撃者に対して無力である。** localStorage の中身は開発者ツールから読める。PBKDF2 が守るのは「保存領域を覗いた者に素のパスワードを渡さない」ことだけであり、進捗データの改竄もアカウントの偽装も、端末上では防げない。

この代償を受け入れられるのは、扱う対象が学習記録に限られるからである。したがって次を守る。

- ログイン画面と設定画面に、端末内完結であることを日本語で明示する（消してはならない）。
- 金銭・個人情報・業務データを扱う機能をこの認証の内側へ置かない（P-102）。

## 実装上の帰結

- パスワードは PBKDF2-HMAC-SHA256 / 600,000 回でハッシュ化する（C-002）。
- 初期パスワードは公開値として扱い、変更するまで学習画面へ入れない。
- 存在しないユーザー名でも同等の計算コストを払い、応答時間からアカウントの有無を読ませない。
- `AuthProvider` の全メソッドを非同期にする。サーバー実装へ差し替えるときシグネチャを変えずに済ませるため。

## 見直しの条件

複数端末での進捗同期が要件になった時点で選択肢 2 を再評価する（Phase 4）。
